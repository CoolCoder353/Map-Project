# Development guide

How to work on Wayfinder: set up, run, test, and make the common kinds of change. For how the
system fits together read [architecture.md](architecture.md) first; settings are in
[configuration.md](configuration.md), endpoints in [api.md](api.md).

## Setup

Node 24+, pnpm 11 and Docker (Docker only for the real stack and the Android build).

```bash
pnpm install
```

In a script or any shell without a terminal, pnpm stops to ask before replacing `node_modules`.
Use `CI=true pnpm install` there.

## Running it

### Fast loop: no Docker

An in-process database (PGlite), demo data, and a fake routing engine that draws smooth curves
instead of following roads. The base map is blank unless a tiles file exists.

The Claude Code preview configs in `.claude/launch.json` start these as `db`, `fake-gh`, `api` and
`web`. By hand, one terminal each:

```bash
pnpm dev:db
```

```bash
pnpm dev:fake-gh
```

```bash
DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/postgres pnpm seed:demo
```

```bash
cd apps/api && DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/postgres JWT_SECRET=dev-secret-dev-secret-dev-secret-0000 TRUST_PROXY=true pnpm dev
```

```bash
pnpm dev:web
```

The routing engine must be running before the seed: the seed snaps the demo trips to roads
through it, and without one they stay unmatched and the coverage map is empty.

Open http://localhost:5173 and sign in as `admin@demo.test` / `demo password`. The demo also has
`dev@demo.test`, `sam@demo.test` and `alex@demo.test`, all with that password, and trips around
Canberra. The database lives in `./data/pglite` and survives restarts; delete that folder to start
again. `PGLITE_DIR` and `PGLITE_PORT` move it.

### Real stack: Docker

Real Postgres, GraphHopper and tiles, as deployed. It needs map data under `./data` (built by the
refresh; see [operations.md](operations.md#map-data-refresh)).

```bash
cd infra && docker compose -f docker-compose.yml -f docker-compose.expose.yml up -d
```

`docker-compose.expose.yml` publishes the API (3000), GraphHopper (8989) and Postgres (5432) on
localhost, for the live checks and benchmark. Don't use `seed:demo` here expecting coverage: its
trips are synthetic lines that don't follow real roads, so a real graph can't match them and the
coverage map stays empty. Upload real trips instead. Caddy serves the site at `https://localhost` with a
locally signed certificate. Create an admin with:

```bash
cd infra && docker compose exec api node dist/cli.js bootstrap-admin you@example.com 'your-password'
```

### Android

The app is Expo; screens are in `apps/mobile/app` (expo-router), the rest in `apps/mobile/src`.
The native map needs a device or emulator, so day to day the Jest screen tests cover the screens
and a real APK covers the rest. Building an APK needs no local Android SDK:

```bash
EXPO_PUBLIC_API_URL=https://maps.paulsjones.com infra/scripts/build-apk.sh
```

`apps/mobile/android/` is generated by `expo prebuild` on every build and is not in git. Change
native settings in `apps/mobile/app.config.ts`, never in the generated project. Installing the
APK is in [install-android.md](install-android.md).

## Tests

| Suite | Command | What and where |
|---|---|---|
| Unit | `pnpm test:unit` | Vitest. `packages/*/test/**`, `apps/{api,worker}/test/unit/**`, and the non-screen mobile tests `apps/mobile/test/*.test.ts` |
| Integration | `pnpm test:integration` | Vitest against a database: `packages/core/test/integration/**`, `apps/{api,worker}/test/integration/**`. In-process PGlite, one file at a time |
| Android screens | `pnpm test:mobile` | Jest (jest-expo + React Native Testing Library): `apps/mobile/test/*.screen.test.tsx` |
| Web end-to-end | `pnpm --filter @wayfinder/web e2e` | Playwright boots its own stack (PGlite, demo seed, fake routing engine, API, Vite): `apps/web/e2e/*.spec.ts` |
| Everything Vitest | `pnpm test` | Unit and integration together |
| Lint and types | `pnpm lint && pnpm typecheck` | |

Before calling a change done, run lint, typecheck, `pnpm test` and `pnpm test:mobile`; add the
end-to-end suite for anything the web app shows. CI (`.github/workflows/ci.yml`) runs all of
these, plus the Android JS bundle and a real Postgres, on every push to `master` and every PR.

On a fresh machine the end-to-end suite first needs a browser:

```bash
pnpm --filter @wayfinder/web exec playwright install chromium
```

Options:

- `TEST_DATABASE_URL=postgres://…` runs integration tests on real Postgres; each file gets a
  throwaway database.
- `GRAPHHOPPER_LIVE_URL=http://localhost:8989` adds tests against a real routing graph (the four
  otherwise skipped).
- `CAPTURE=1` makes the end-to-end run capture design-review screenshots instead.

Test helpers:

- `packages/core/test/helpers`: `createTestDb()` (migrated database), `FakeQueue` (records jobs
  instead of running them; `queue.take(name)`), `makeUser()`, `straightPath()` for fake routes.
- `apps/api/test/helpers/app.ts`: `createTestApp()` (the Fastify app on a test database) and
  `tokenFor(app, user, role)`.
- `apps/mobile/test/mocks.tsx`: mocks for native modules and app services in screen tests.
  Screen tests render with `await render(...)`: React Native Testing Library 14 is async.

## Making common changes

### An API endpoint

1. Request and response schemas in `packages/shared/src/schemas/<area>.ts` (exported through
   `index.ts`).
2. The logic in a service in `packages/core/src/services/`, taking `db` (and other dependencies)
   as arguments so tests can pass fakes.
3. The route in `apps/api/src/routes/<area>.ts`: `parse(Schema, req.body)` to validate, then
   call the service. Routes register in `apps/api/src/app.ts`.
4. An integration test in `apps/api/test/integration/`.
5. If the Android app calls it, add it to `scripts/verify-mobile-contract.ts`.
6. Add it to [api.md](api.md).

### A database change

Add the next numbered file in `packages/core/src/db/migrations/` (`007_what_it_does.sql`). Never
edit a migration that has run anywhere: it is recorded in `schema_migrations` by file name and
won't run again. Migrations run in order, one transaction each, when the API and worker start and
in every test database. Removing or renaming a column the Android app reads breaks installed
apps until they update, so say so in the commit and in [deploy-small-server.md](deploy-small-server.md#keeping-the-phone-app-in-step).

### A background job

The handler goes in `apps/worker/src/jobs.ts`; a schedule, if any, in `apps/worker/src/main.ts`
(`boss.schedule`). Queue work from a service with `queue.send(name, data, { singletonKey })`.
Handlers must be safe to retry: pg-boss retries failures. Add it to the jobs table in
[architecture.md](architecture.md#background-jobs).

### Words people read

User-facing copy that varies with the app's voice lives in `packages/shared/src/copy.ts`, in
three voices (`plain`, `playful`, `minimal`); the type makes you write all three. Coverage is
**roads travelled**: hexagons are internal and never named to users.

### The places import (search data)

The pipeline is `apps/worker/src/pipeline/` (`osm-places.ts` maps OSM tags, `boundaries.ts` and
`import-places.ts` locate places). Unit-test tag handling in `apps/worker/test/unit/`. Rebuild
only the places, about 7 minutes on Australia:

```bash
cd infra && docker compose run --rm --no-deps worker node dist/refresh-cli.js places
```

For the Queensland server, rebuild into its build database and ship with
`deploy-small.sh places` ([deploy-small-server.md](deploy-small-server.md)).

### Routing and explore

`packages/core/src/services/routing.ts` builds requests; `packages/core/src/lib/graphhopper.ts` is
the client; scoring is `packages/shared/src/novelty.ts`. GraphHopper settings, including which
encoded values exist, are in `infra/graphhopper/config.yml`; changing encoded values needs a
graph rebuild. `pnpm bench:explore 50000 20` checks explore stays under its targets.

## Releasing

1. Checks green (above).
2. Deploy the server: [operations.md](operations.md#upgrading) for a full-size server,
   [deploy-small-server.md](deploy-small-server.md) for the live Queensland one.
3. `pnpm verify:stack` and `pnpm verify:mobile` against it.
4. If the Android app changed, or the API changed shape, build a new APK and share it.
5. Record anything notable in [verification.md](verification.md).

## Gotchas

- **Workspace packages export TypeScript source** under the `development` export condition. The
  repo scripts pass `--conditions=development` to `tsx`; a new script needs it too.
- **The Android build runs pnpm inside Docker** on your checkout. `build-apk.sh` restores
  `node_modules` afterwards; if a build is interrupted, run `CI=true pnpm install`.
- **The APK's server address is fixed at build time.** Wrong address, broken app: every screen
  says "Can't reach …". The build script checks it.
- **`POSTGRES_PASSWORD` only applies when the database volume is created.** Changing `.env`
  afterwards makes the API and worker fail with `28P01`. See
  [operations.md](operations.md#rotating-secrets).
- **The fake routing engine** answers routes, isochrones and map matching with straight lines
  and curves, not roads; test real routing behaviour against a graph.
- **Coordinates are `[lon, lat]`** everywhere, as GeoJSON has them.
