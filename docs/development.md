# Development guide

How to work on Wayfinder: set up, run, test, and make the common kinds of change. For how the
system fits together read [architecture.md](architecture.md) first; settings are in
[configuration.md](configuration.md), endpoints in [api.md](api.md).

## Setup

Node 24+, pnpm 11 and Docker (Docker only for the real stack and the Android build).

```bash
pnpm install
```

In a script or any shell without a terminal, pnpm stops to ask before replacing `node_modules`.
Use `CI=true pnpm install` there.

## Running it

### Fast loop: no Docker

An in-process database (PGlite), demo data, and a fake routing engine that draws smooth curves
instead of following roads. The base map is blank unless a tiles file exists.

The Claude Code preview configs in `.claude/launch.json` start these as `db`, `fake-gh`, `api` and
`web`. By hand, one terminal each:

```bash
pnpm dev:db
```

```bash
pnpm dev:fake-gh
```

```bash
DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/postgres pnpm seed:demo
```

```bash
cd apps/api && DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/postgres JWT_SECRET=dev-secret-dev-secret-dev-secret-0000 TRUST_PROXY=true pnpm dev
```

```bash
pnpm dev:web
```

The routing engine must be running before the seed: the seed snaps the demo trips to roads
through it, and without one they stay unmatched and the coverage map is empty.

Open http://localhost:5173 and sign in as `admin@demo.test` / `demo password`. The demo also has
`dev@demo.test`, `sam@demo.test` and `alex@demo.test`, all with that password, and trips around
Canberra. The database lives in `./data/pglite` and survives restarts; delete that folder to start
again. `PGLITE_DIR` and `PGLITE_PORT` move it.

### Real stack: Docker

Real Postgres, GraphHopper and tiles, as deployed. It needs map data under `./data` (built by the
refresh; see [operations.md](operations.md#map-data-refresh)).

```bash
cd infra && docker compose -f docker-compose.yml -f docker-compose.expose.yml up -d
```

`docker-compose.expose.yml` publishes the API (3000), GraphHopper (8989) and Postgres (5432) on
localhost, for the live checks and benchmark. Don't use `seed:demo` here expecting coverage: its
trips are synthetic lines that don't follow real roads, so a real graph can't match them and the
coverage map stays empty. Upload real trips instead. Caddy serves the site at `https://localhost` with a
locally signed certificate. Create an admin with:

```bash
cd infra && docker compose exec api node dist/cli.js bootstrap-admin you@example.com 'your-password'
```

### Android

The app is Expo; screens are in `apps/mobile/app` (expo-router), the rest in `apps/mobile/src`.
The native map needs a device or emulator, so day to day the Jest screen tests cover the screens
and a real APK covers the rest. Building one needs only Docker; the whole routine, from the
checks before a build to sharing the file, is in [build-android.md](build-android.md):

```bash
EXPO_PUBLIC_API_URL=https://maps.coolcodertech.com infra/scripts/build-apk.sh
```

`apps/mobile/android/` is generated by `expo prebuild` on every build and is not in git. Change
native settings in `apps/mobile/app.config.ts`, never in the generated project. Installing the
APK is in [install-android.md](install-android.md).

#### Emulator

An Android 16 emulator runs without a window and is driven with `adb`. It needs hardware
virtualisation (`/dev/kvm`; switch on SVM or VT-x in the BIOS). Setup is one-off, puts a JDK and
the Android SDK under `~/Android` (about 6 GB), and needs no system packages:

```bash
infra/scripts/android-emulator.sh setup
```

```bash
infra/scripts/android-emulator.sh start
```

```bash
infra/scripts/android-emulator.sh install
```

`install` takes an APK path (default `dist/wayfinder.apk`) and opens the app; `stop` shuts the
emulator down. The APK already includes x86_64 code, so the same file runs on phones and the
emulator. For screenshots, taps, typing and GPS use the [device harness](#device-harness); for
anything it doesn't do, `adb` directly (`~/Android/Sdk/platform-tools/adb`):

| To | Run |
|---|---|
| See the screen | `adb exec-out screencap -p > screen.png` |
| Tap, type, go back | `adb shell input tap 540 1200`, `adb shell input text hello`, `adb shell input keyevent BACK` |
| Read what's on screen | `adb shell uiautomator dump /dev/stdout` |
| Crashes and app logs | `adb logcat -d \| grep -iE "AndroidRuntime\|ReactNativeJS\|maplibre"` |
| Set the GPS position | `adb emu geo fix 153.0251 -27.4698` (lon then lat) |
| Force Doze | `adb shell dumpsys deviceidle force-idle` |

An APK built for `maps.coolcodertech.com` talks to the live server, which has real users: look,
but don't sign in with a real account or create data there. To test against the local
dev stack, build with `EXPO_PUBLIC_API_URL=http://10.0.2.2:3000 ALLOW_HTTP=1` (`10.0.2.2` is this
machine as the emulator sees it), and don't hand that APK to anyone.

#### Device harness

`pnpm device …` drives Wayfinder on a registered phone, with Google's Desktop Head Unit (DHU) for
the Android Auto screen, or on the emulator: screenshots of both screens, taps by name or
position, typing, the phone's and the car's GPS, and replaying a drive. It's for Claude and for
people checking by eye; its own logic is tested in `scripts/test/device`. Android Auto doesn't
run on an emulator (Play won't install it there), so the car side needs a real phone.

One-off setup, in order:

1. `sdkmanager "extras;google;auto"` for the DHU, and `libc++` (Arch: `sudo pacman -S libc++`;
   Debian: `libc++1 libc++abi1`).
2. A Wayfinder account for testing on the server, made an admin, with **Test account** switched
   on in `/admin` (its drives then don't count towards learned speeds or light timings). The
   person who owns the phone creates it; the harness never sees its password.
3. `pnpm device account <that email>`, and for a phone `pnpm device register <serial>`
   (`pnpm device devices` shows it). Both are kept in `.harness/config.json`, which git ignores.
4. On the phone, by its owner: Android Auto's developer settings (tap its version ten times),
   **Unknown sources** on, and **Start head unit server** from its ⋮ menu (again after each
   restart).
5. Before each session, sign Wayfinder in to the test account.

Connect the phone over **wireless debugging** (Developer options → Wireless debugging; `adb pair
<ip:port>` with the pairing code, then `adb connect <ip:port>` and `pnpm device register <ip:port>`).
On the first phone run USB dropped every few seconds with Android Auto installed.

| Command | Does |
|---|---|
| `up [--car] [--window] [--emulator]` | Checks Wayfinder is signed in to the test account (closing the notification shade, and waiting for Settings to show it); `--car` starts the head unit (`--window` to watch it), pauses any music Android Auto starts and puts Wayfinder back in front. A session left by an `up` that stopped, or by a restart, is picked up, not refused |
| `shot phone\|car` | Screenshot to `.harness/shots/`; prints the path |
| `ui` | What's on the phone's screen, and where to tap it |
| `tap <text>`, `tap <x> <y>`, `tap car <x> <y>` | Tap by visible text or position. Car positions are in the `shot car` picture (800×480); with the rotary controller on, the head unit's own grid is the same (`carTapScale` in `.harness/config.json` for a head unit that differs; a run without the controller measured 1.16) |
| `type <text>`, `key back\|home\|enter`, `swipe x1 y1 x2 y2` | Text and keys on the phone |
| `gps <lon> <lat> [--car]`, `gps reset` | Move the car (and the emulator's GPS) (`[lon, lat]`, as everywhere). **A real phone's own GPS is never faked**: Play services' location reads a faked provider, so every other app on the phone (location sharing, home automation) would see the fake position. Wayfinder follows the car's position while it comes, the phone's otherwise |
| `drive <route.geojson\|.gpx> [--speed 50]` | Replay a route a fix a second through the head unit (needs `up --car` on a phone); `scripts/device/routes/` has a rough one from the CBD to Mt Coot-tha |
| `car day\|night`, `car key home\|back\|search\|navigation`, `car restrict on\|off` | The head unit's own controls |
| `car focus`, `car scroll up\|down [n]`, `car select` | The rotary controller. Its focus starts in the rail (mic, layout, app icons): `focus` moves it into the app's list. Then each turn moves one row and scrolls the list (the console has no swipe), and `select` presses the row it's on |
| `logs` | App and car logs since the last look. Each spoken direction is logged as `said: …` (or `not said …` when another app has the audio), for a PC with no sound card |
| `install <apk>` | Emulator only |
| `down [--stay-signed-in]` | Stop the head unit, turn the test location off, and sign the test account out unless `--stay-signed-in`. Only the phone's owner can sign it back in, so to restart the head unit run `up --car` again instead |

What it won't do, whatever it's asked:

- Act on a phone that isn't registered, or pick one when several are attached and none is named.
- Send anything to a phone but looking, tapping, typing, a test location and the head unit's
  port: no installing, uninstalling, clearing data, deleting files, rebooting or changing settings
  (`scripts/device/adb.ts` is the only place commands are built).
- Tap outside Wayfinder (and its permission prompts), or tap Sign out or Delete account; tap the
  car screen unless the car app's log says Wayfinder is showing (the car app logs "car screen
  shown" again every 15 s while it is, so the line survives a busy log), or off the car screen.
- Fake a real phone's own GPS.
- Change anything unless Wayfinder is signed in to the test account; it stops if the sign-in
  screen appears.
- Move the GPS on an app older than versionCode 17, whose upload queue could send a test drive as
  the next account to sign in.
- Change anything in `/admin`: Claude looks there, and asks before changing anything on the
  testers' server.

`down` undoes the phone changes. Ctrl-C during `drive` only stops the drive. To undo them by hand (the test
provider only after an older harness, which faked the phone's GPS):
`adb shell cmd location providers remove-test-provider gps`,
`adb shell appops set com.android.shell android:mock_location deny`, `adb forward --remove tcp:5277`,
and on the phone Android Auto's ⋮, **Stop head unit server** (its developer settings can be turned
off from the same menu).

## Tests

Every feature is tested, and every change passes the whole suite. The rule, where each kind of
test goes, the test harnesses and a map of what tests what are in [testing.md](testing.md).

```bash
pnpm check
```

That's lint, types, every Vitest project (unit, integration on PGlite, web components) and the
Android tests with their coverage floors, then Playwright, then the Android Auto module's Kotlin
tests. While working, `pnpm test`, `pnpm test:mobile` and `pnpm test:e2e` run the pieces, and
`CI=true pnpm test:android` the Kotlin ones.

## Making common changes

### An API endpoint

1. Request and response schemas in `packages/shared/src/schemas/<area>.ts` (exported through
   `index.ts`).
2. The logic in a service in `packages/core/src/services/`, taking `db` (and other dependencies)
   as arguments so tests can pass fakes.
3. The route in `apps/api/src/routes/<area>.ts`: `parse(Schema, req.body)` to validate, then
   call the service. Routes register in `apps/api/src/app.ts`.
4. An integration test in `apps/api/test/integration/`: success, validation, who may call it.
5. Tests for each screen that uses it: `apps/web/test` (declare the endpoint in the fake API)
   and `apps/mobile/test`.
6. If the Android app calls it, add it to `scripts/verify-mobile-contract.ts`.
7. Add it to [api.md](api.md), and the feature to [testing.md](testing.md#what-tests-what).

### A database change

Add the next numbered file in `packages/core/src/db/migrations/` (`007_what_it_does.sql`). Never
edit a migration that has run anywhere: it is recorded in `schema_migrations` by file name and
won't run again. Migrations run in order, one transaction each, when the API and worker start and
in every test database. Removing or renaming a column the Android app reads breaks installed
apps until they update, so say so in the commit and in [deploy-small-server.md](deploy-small-server.md#keeping-the-phone-app-in-step).

### A background job

The handler goes in `apps/worker/src/jobs.ts`; a schedule, if any, in `apps/worker/src/main.ts`
(`boss.schedule`). Queue work from a service with `queue.send(name, data, { singletonKey })`.
Handlers must be safe to retry: pg-boss retries failures. Test the handler in
`apps/worker/test/integration/jobs.test.ts`, and a schedule in `register.test.ts`. Add it to the
jobs table in [architecture.md](architecture.md#background-jobs).

### Words people read

User-facing copy that varies with the app's voice lives in `packages/shared/src/copy.ts`, in
three voices (`plain`, `playful`, `minimal`); the type makes you write all three, and
`packages/shared/test/copy.test.ts` fails on any that names hexagons, cells or fog. Coverage is
**roads travelled**: hexagons are internal and never named to users.

### The places import (search data)

The pipeline is `apps/worker/src/pipeline/` (`osm-places.ts` maps OSM tags, `boundaries.ts` and
`import-places.ts` locate places). Unit-test tag handling in `apps/worker/test/unit/`. Rebuild
only the places, about 7 minutes on Australia:

```bash
cd infra && docker compose run --rm --no-deps worker node dist/refresh-cli.js places
```

For the Queensland server, rebuild into its build database and ship with
`deploy-small.sh places` ([deploy-small-server.md](deploy-small-server.md)).

### Routing and explore

`packages/core/src/services/routing.ts` builds requests; `packages/core/src/lib/graphhopper.ts` is
the client; scoring is `packages/shared/src/novelty.ts`. GraphHopper settings, including which
encoded values exist, are in `infra/graphhopper/config.yml`; changing encoded values needs a
graph rebuild. `pnpm bench:explore 50000 20` checks explore stays under its targets.

### Changing the car app

The Android Auto app is Kotlin in `apps/mobile/modules/wayfinder-car` ([architecture.md](architecture.md#android-auto)
says how it fits together). Don't put native code in `apps/mobile/android/`: it is generated.

- **A new thing the car asks the phone for** (a bridge request) needs all of these: a schema in
  `apps/mobile/src/car/protocol.ts`, a parser in `bridge/Protocol.kt`, a fixture in
  `modules/wayfinder-car/android/src/test/resources/fixtures` that both `carProtocol.test.ts` and
  `ProtocolTest.kt` read, a handler in `src/car/handlers.ts`, and a method on `CarApi` (with
  `BridgeCarApi.kt` sending it and `FakeCarApi` in the Kotlin tests answering it). `carModule.test.ts`
  fails if `BridgeCarApi.kt` sends a request `handlers.ts` doesn't answer.
- **A screen** puts its map scene up with `Screen.show(map, scene)` (`screens/ScreenKit.kt`), which
  only draws while the screen is on top. Test it with the helpers in `modules/wayfinder-car/android/src/test/java/app/wayfinder/car`.
- Run the Kotlin tests with `CI=true pnpm test:android` (it takes over `node_modules` while it
  runs, so run nothing else then), and the JavaScript side with `pnpm test:mobile` and `pnpm test`.
- Try it in the Desktop Head Unit: [build-android.md](build-android.md#trying-it-in-a-car). The
  checklist in [verification.md](verification.md#android-auto-desktop-head-unit) lists what only
  the head unit shows, such as the map drawing on the car surface.

## Releasing

1. `pnpm check` passes.
2. Deploy the server: [operations.md](operations.md#upgrading) for a full-size server,
   [deploy-small-server.md](deploy-small-server.md) for the live Queensland one.
3. `pnpm verify:stack` and `pnpm verify:mobile` against it.
4. If the Android app changed, or the API changed shape, build a new APK and share it
   ([build-android.md](build-android.md)).
5. Record anything notable in [verification.md](verification.md).

## Gotchas

- **Workspace packages export TypeScript source** under the `development` export condition. The
  repo scripts pass `--conditions=development` to `tsx`; a new script needs it too.
- **The Android build runs pnpm inside Docker** on your checkout. `build-apk.sh` restores
  `node_modules` afterwards; if a build is interrupted, run `CI=true pnpm install`.
- **The APK's server address is fixed at build time.** Wrong address, broken app: every screen
  says "Can't reach …". The build script checks it. People can still change it on the sign-in
  screen; what they type is tidied up (`maps.example.org/` becomes `https://maps.example.org`).
- **Expo native modules must match the Expo SDK.** One from another SDK compiles, passes every
  Jest test (Jest mocks native modules) and then kills the app on launch; that shipped once with
  `expo-contacts`. After touching a native dependency, run `npx expo install --check` in
  `apps/mobile` and open a new APK on the [emulator](#emulator). `expo-contacts` 57's main entry
  is a new API whose old functions throw, so the app imports `expo-contacts/legacy`.
- **The Android app must survive what the phone throws at it.** Location switched off, a
  permission refused, secure storage unreadable, a server that never answers: catch it where it
  happens and say so on screen. A render error anywhere shows `src/ui/ScreenError.tsx` (Expo
  Router's `ErrorBoundary`, exported from `app/_layout.tsx`) instead of closing the app, and API
  requests give up after 30 s (`timeoutMs` to change it). Pass the shared schema (`schema:`) for
  an answer a screen reads fields from: an APK and the server are updated separately.
- **`POSTGRES_PASSWORD` only applies when the database volume is created.** Changing `.env`
  afterwards makes the API and worker fail with `28P01`. See
  [operations.md](operations.md#rotating-secrets).
- **The fake routing engine** answers routes, isochrones and map matching with straight lines
  and curves, not roads; test real routing behaviour against a graph.
- **Coordinates are `[lon, lat]`** everywhere, as GeoJSON has them.
